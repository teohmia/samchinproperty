## Listings — how to add/update them
All listings live in one file: **`data/listings.json`**. It currently has 14 real listings pulled from Sam's PropertyGuru profile — 7 For Sale and 7 For Rent (see "Current listings" above) — all of which now have real photos. To add or edit one, add/update an object in the array. `data/listings.example.json` shows the exact format with two filled-in examples — copy an entry from there and edit the values. Note: The Iveria appears twice — once for sale (`the-iveria`) and once for rent (`the-iveria-rent`), since it's the same building but a different unit/listing — the `id` just needs a `-rent` suffix to avoid clashing with the sale entry whenever the same building is listed both ways.

If you send listing updates over to me, that's all handled automatically. If you (or anyone else) ever edit `data/listings.json` directly by hand, run `node build.js` from inside the `site` folder afterward — it copies the new data into the fallback copies baked into the HTML pages (see "Previewing locally" below) so everything stays in sync. Skipping this step doesn't break the live/hosted site (it always reads `data/listings.json` directly), it just means the double-click/offline preview and the SEO fallback content would show the old data until the next `node build.js` run.

Fields per listing:
- `id` — a short unique slug (used in the listing's URL, e.g. `listing.html?id=orchard-residences-3br`)
- `type` — `"sale"` or `"rent"`
- `featured` — `true` to show it in the homepage "Featured Listings" strip (top 3 featured listings are shown)
- `title`, `district`, `propertyType` (e.g. `"Condominium"`, `"Landed"`, `"HDB"`), `price`, `priceSuffix` (e.g. `"/mo"` for rentals, blank for sales)
- `beds`, `baths`, `sqft` (numbers), `tenure` (e.g. `"Freehold"`, `"99-year Leasehold"`, blank if not applicable)
- `description` — a short paragraph, shown under "About This Property" on the listing page
- `amenities` — an array of short strings (e.g. `["Pool", "Gym", "24hr Security"]`), shown as "Facilities" under About This Property
- `nearby` — an array of short strings for MRT stations, malls, schools, parks etc. (e.g. `["Orchard MRT — 5 min walk", "ION Orchard"]`), shown under "What's Nearby"
- `images` — an array of photos (first one is used as the card thumbnail); leave as `[]` if no photos yet and a placeholder will show instead. Each entry can be either a plain path string (e.g. `"images/listings/foo/kitchen.jpg"`), or — preferred, for SEO/accessibility — an object with `src` and `alt`, e.g. `{ "src": "images/listings/foo/foo-kitchen.jpg", "alt": "Foo kitchen with island and city view" }`. The `alt` text is used everywhere that photo appears (card thumbnail, gallery hero, filmstrip thumbnail, and the `schema.org` structured data's image field), so write it as a real description of what's in the shot, not a filename. Both formats can be mixed in the same array; a plain string just gets no alt text (falls back to the listing title). See `data/listings.example.json` and the `up-robertson-quay` entry in `data/listings.json` for a filled-in example.
- `lat`, `lng` — decimal coordinates for the map pin (see "Map" below for how these were set and how to add them for new listings)

On the listing detail page, `price`, `propertyType`, `tenure`, `sqft`, `beds`, `baths` and `district` are also assembled automatically into a "Property Details" table, with a price-per-sqft figure calculated from `price` and `sqft` — no separate field needed for that.

When you have real listing content and photos ready to send over, this is the format to drop them into — just send the details and I'll add the entries (or you can edit `data/listings.json` directly, it's plain text).

If a listing has no photos yet, or listings.json fails to load, the site shows a graceful placeholder/empty state instead of breaking — and still links out to Sam's PropertyGuru and Huttons profiles as a fallback, so there's always somewhere for a visitor to look even before the on-site inventory is filled in.

**Photo gallery**: on the listing detail page, the first `images` entry shows large as the "hero" photo, with the rest as a horizontal-scrolling filmstrip underneath (swipe or trackpad-scroll sideways — it never stacks photos in a long vertical column). Clicking a thumbnail, or the ← / → arrows on the hero photo, swaps the hero image. Any filename containing "floor-plan" (e.g. `up-robertson-quay-floor-plan.jpg`) is automatically shown in full rather than cropped to fill the frame, since a floor plan needs to be read whole. The gallery is capped at `max-width: 760px` (in `css/styles.css`) rather than stretching edge-to-edge on a wide desktop screen — most listing photos (Up@Robertson Quay's included) are Sam's own phone/screenshot photos rather than professional HD shots, and blowing them up to fill a ~1180px-wide page only makes the softness more obvious. If a listing later gets proper high-resolution photography, that cap can be raised or removed.

**Photo filenames**: for SEO, name photo files descriptively rather than generically — `up-robertson-quay-swimming-pool.jpg` rather than `IMG_4821.jpg` or `03.jpg`. Search engines and image search do read filenames as a (small) ranking signal, on top of the `alt` text described above.

**Cleaning up screenshot photos**: if a photo started life as a screenshot (e.g. a phone screen-recording or a screenshotted listing photo), it can pick up a thin dark line or border artifact along one edge from how the screenshot was cropped. Worth a quick visual check before adding new photos — crop any such line out in an image editor (or ask me to do it programmatically: a script can detect a near-solid, near-black strip along an edge and trim just that, without touching real photo content) before resizing/compressing and dropping the file into `images/listings/<listing-id>/`.

**Filters**: For Sale and For Rent each have a filter bar above the grid — District, Property Type, Price Range, and Bedrooms — built from whatever's actually in `data/listings.json` (district, property type and bedroom options are generated from the real data; price brackets are fixed ranges tuned separately for sale prices vs. monthly rent, defined in `priceBrackets()` in `js/main.js` — adjust the numbers there if listings start skewing outside those bands). The same District/Property Type/Price Range filters also appear in the homepage search card — see "Pages" above.

**Mobile pagination**: on phones (≤900px, the same breakpoint the layout already switches at), the For Sale and For Rent grids show 4 listings at a time with "&larr; Prev / Page X of Y / Next &rarr;" controls underneath, instead of one long scroll of every matching listing. Desktop is unaffected — it still shows everything at once alongside the map, same as before. This is handled in `initListingGrid()` in `js/main.js`: changing a filter always resets back to page 1 (so you never land on an empty "page 3 of 1" after narrowing the results), and resizing across the breakpoint (or rotating a phone) re-checks immediately. The page size (`MOBILE_PAGE_SIZE`, currently `4`) is a single constant near the top of that function if you ever want it different.

## Previewing locally
Browsers block a page opened as a `file://` link (i.e. double-clicked) from reading other local files with JavaScript — so a live `fetch('data/listings.json')` always fails when previewed this way. This is a browser security restriction, not a bug, and it can't be worked around directly.

To get around it, `index.html`, `for-sale.html`, `for-rent.html` and `listing.html` each carry a hidden inline copy of the listings data (a `<script type="application/json" id="listings-inline-data">` block — look for the `BUILD:INLINE-DATA` comment markers). When the live fetch fails — which it always does under `file://` — the site quietly falls back to that inline copy instead, so listings, filters and detail pages all work the same whether you're just double-clicking the files or it's hosted for real. `for-sale.html` and `index.html` additionally have their current listings written directly into the visible HTML too (on top of the inline fallback), purely for search-engine purposes — see "SEO" below.

The only thing that genuinely needs real hosting or a local server is Google Fonts and the map tiles, which need actual internet access rather than a browser restriction — those will just silently not load in a fully offline preview, everything else on the page still works.

If you ever want to preview through a real local server instead (closer to how a real visit behaves, and needed if you're offline entirely): run `python3 -m http.server` from inside the `site` folder, then open `http://localhost:8000`. Uploading the folder to any real web host works the same way once live.

## Map
The map on the category pages uses [Leaflet](https://leafletjs.com/) with free Esri basemap tiles (`server.arcgisonline.com`, the classic REST tile services — light grey canvas + a labels layer on top) — no API key, no account, no cost. (Plain `tile.openstreetmap.org` is reserved for light, non-app traffic and actively blocks embedded/app usage per its own policy — see osm.wiki/Blocked. This site used CARTO's basemap tiles at first, but CARTO has since started requiring you to sign up for a free API key even for basic use, so it was swapped for Esri's, which doesn't need one — if a map ever shows tiles stamped "API key required" again, that's this same kind of provider policy change, and it means the tile URL in `addBasemapTileLayer()` in `js/main.js` needs swapping again.)

**Pins**: each listing with `lat`/`lng` set gets its own pin on the map, badged with a compact price (e.g. `$1.4M`, `$680K` for sale, or `$5K/mo` style for rent). Clicking a pin pops up the listing name, price and a "View listing →" link straight to that property's page. The map auto-zooms/pans (`fitBounds`) to frame whichever listings are showing for that page and filter state. If a page ever has no listings with coordinates (both For Sale and For Rent currently have listings with coordinates), the map falls back to showing Sam's five core coverage districts as plain gold pins (defined in `js/main.js` as `SERVICE_AREAS`), so the map is never empty.

**Clustering**: several listings sit only a few hundred metres apart (e.g. the River Valley / CBD cluster), so at a zoom that still fits every listing on the page, their price badges would otherwise land on top of each other and become unreadable. [Leaflet.markercluster](https://github.com/Leaflet/Leaflet.markercluster) groups pins that are too close together at the current zoom into a single round "N homes" badge — click it to zoom in, and it splits back into normal price pins once there's room. This needs its own small CSS/JS files loaded alongside Leaflet's own (see the `<link>`/`<script>` tags for `leaflet.markercluster` near the top/bottom of `for-sale.html` and `for-rent.html`) — if that library ever fails to load for some reason, the map still works, it just shows all pins unclustered instead.

The "enough room" threshold (`maxClusterRadius` in `initListingMap()` in `js/main.js`, currently `85`) is measured pin-to-pin, but each price badge is a label roughly 65–90px *wide*, centered on its pin — so pins need to be that far apart, not just a few pixels, before two badges stop overlapping. If badges ever start overlapping again after splitting out of a cluster (most likely if a future listing's price format runs noticeably longer, e.g. a rental with a "/mo" suffix, or if the badge's own font/padding in `css/styles.css` is made bigger again), raise that number a bit further.

The badge itself sits inside a Leaflet marker wrapper that's deliberately 0×0 pixels (so the label can be visually bigger than its own anchor point) — `.price-pin-badge` and `.price-pin-cluster-badge` in `css/styles.css` both need `display: inline-block` to still size themselves to their own text in that situation (a plain block-level box would instead try to fill its 0px-wide parent and let the text spill out uncontained). Keep that rule if you ever restyle these.

**Important caveat on the coordinates**: the `lat`/`lng` values currently in `data/listings.json` are hand-estimated from each property's known address/area — they were **not** run through a geocoding service, because this working environment's network access blocks calls to geocoding APIs (e.g. OpenStreetMap/Nominatim). They should be close (right neighbourhood, right general spot), but **please double-check pin placement against Google Maps before the site goes live** — search each address and compare to where the pin lands, and adjust the `lat`/`lng` numbers in `data/listings.json` if a pin is off. For any new listing you add, get its coordinates by right-clicking the exact spot on Google Maps and copying the two numbers it shows (or asking me to add it, then double-checking placement the same way) — then run `node build.js` afterward as usual.

## SEO
This site is built to be findable both for generic searches ("Singapore property for sale/rent") and for people searching a specific project name (e.g. "Sky Everton for sale"):
- Every page has its own `<title>` and meta description; `listing.html` additionally sets a unique title/description per property via JavaScript once the listing loads, and injects `schema.org` `RealEstateListing` structured data (price, address, agent, and a photo) so search engines can understand it as a real listing, not just text.
- Photos use descriptive filenames and per-photo `alt` text (see "Listings" above) — both are small but real ranking signals for image search, and `alt` text also makes the site usable with a screen reader.
- The For Sale grid and homepage "Featured" strip have their current listings written directly into the HTML (not only added by JavaScript after the page loads), so a search engine's first read of the page already sees the real property names, prices and links — this matters because not every crawler renders JavaScript reliably. The JavaScript then re-renders the same grid on top for filtering/interactivity. Run `node build.js` after hand-editing `data/listings.json` to keep this in sync (see "Listings" above) — it's a bonus for search engines and offline preview, not required for the live site to work correctly either way.
- `robots.txt` and `sitemap.xml` are included, listing every page and every individual listing URL. **Before going live**, replace `REPLACE-WITH-YOUR-DOMAIN` in both files with the real domain, then submit the sitemap in Google Search Console (free) — this is what gets new listings indexed quickly rather than waiting for Google to stumble on them.
- `listing.html?id=...` uses one physical file for every listing (content swapped by JavaScript based on the `id` in the URL) rather than a separate HTML file per property. This works for search engines that render JavaScript (Google does), but if you want the strongest possible SEO later, the next step up would be generating a real static HTML file per listing at deploy time — worth revisiting once there's a steady flow of listings to justify it.
